# Расширение №1: обучение или проверяемое вычисление?

Вопрос: на фиксированном небольшом научном benchmark как соотносятся SFT, DPO и исполнение арифметического выражения, предложенного моделью?

`src/scireason/toolstudy.py` создаёт новый датасет, выполняет генерацию и ограниченный AST-калькулятор, сохраняет каждое предсказание и строит первичную таблицу. `training.py` использует прежние реальные TRL SFT/DPO pipelines, но другой `data_root`. Конфигурации для трёх seeds находятся в `configs/toolstudy/`. `scripts/run_toolstudy.sh` запускает весь эксперимент с восстановлением завершённых тренировок. Исходные опубликованные результаты не смешиваются с новым исследованием.

## Два режима ответа

Direct ожидает JSON с числом/категорией/null и явным abstain. Calculator ожидает ту же структуру, но числовой ответ может быть строкой арифметического выражения. Модель сама должна выбрать формулу и числа; эталонная формула ей не показывается. Исполнитель разрешает только ограниченные арифметические операции и sqrt. Он не использует Python eval, не открывает файлы и не вызывает сеть.

Это сравнение двух целых pipelines: меняется инструкция и добавляется исполнитель. Оно не изолирует чистый эффект калькулятора при неизменном prompt. В SFT нет обучения на программах, поэтому перенос к формату выражения сам является изменением распределения инструкций. Если модель не выдаёт нужный JSON, выполнение не начинается. Нельзя объявлять такое отсутствие улучшения доказательством бесполезности инструментов.

## Научный контроль

384 обучающих, 64 validation и два независимых числовых набора по 144 задачи. Четыре problem families отсутствуют в train/validation. OOD test и final используют общие шаблоны с разными числовыми условиями: это ограничение явно записано. Числовые условия отслеживаются отдельно от формулировок; перестановка чисел не позволяет незаметно пересечь split.

Числовой эталон вычисляется через Decimal независимо от AST-исполнителя. Проверяются правильность chosen, неправильность rejected, отсутствие пересечения условий и безопасность синтаксиса. Все настройки заморожены до сравнений. По три запуска SFT и DPO проверяют вариацию оптимизации, но не превращают один benchmark в три независимых набора задач.

## Объективы

SFT минимизирует отрицательный log likelihood токенов ответа, маскируя prompt и padding. DPO сравнивает chosen/rejected через разность log probability ratios к замороженному SFT reference, beta=0.1. Для каждого seed используется собственный SFT adapter и его копия-reference. Градиенты обновляют LoRA policy, а не reference или эталонный калькулятор.

Падение training loss не доказывает улучшения арифметики. В частности, модель может лучше усвоить шаблон JSON и поведение abstain, продолжая ошибаться в числах. Поэтому отдельно сохраняются numeric accuracy, format compliance, abstention, ID/OOD и результаты по семействам.

## Как читать честный отрицательный результат

Строгая accuracy требует одновременно правильного значения и формата. После наблюдения ошибок baseline добавлена **post-hoc диагностика значения**: она допускает числовые строки и игнорирует лишние/отсутствующие поля. Эта диагностика не заменяет исходную метрику и не доказывает надёжное следование инструкциям. Сырые ответы не редактируются. Неудачный первый DPO-запуск из-за типа learning rate также сохранён в журнале.

Измеренные результаты: `reports/toolstudy/research_report.md`, `metrics.json`, `diagnostics.json`, `seed_summary.json`, `paired.json`. Пока прогон не завершён, отсутствие файла означает NOT RUN, а не нулевую метрику. Paired bootstrap по задачам показывает неопределённость условно на этом наборе; не охватывает другие семейства, модели и данные pretraining.

Упражнение: вручную проверьте десять предсказаний, разделив ошибку формата, выбора операции и исполнения. Затем предложите заранее зафиксированный эксперимент с обучением на программах и новым отложенным набором. Не подбирайте prompt на текущем final.

Идея отделить генерацию программы от её исполнения связана с [PAL](https://arxiv.org/abs/2211.10435). Здесь используется гораздо более узкий арифметический язык и маленькая модель; результаты PAL не являются результатами этого проекта.
